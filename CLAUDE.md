# Binnacle — context for Claude

> **ABSOLUTE RULE — NOTHING TO THE CAR.** Nothing in this project ever sends anything onto the car's CAN bus or otherwise affects the car itself. The dash app *subscribes* to the stock CAN service and *receives* data; a write to the dash's own MCU is the one narrow exception, only as set out under "MCU writes" below. This is enforced in code (for the CAN feed one class, two allowed binder calls: subscribe/unsubscribe; the only other binder use is `CarPlayLink` to xcertplay, an app on the unit, see "CarPlay in the dash") and by build-time guards that refuse to build if any write path is referenced: `app/tools/check_readonly.sh` on the source and `app/tools/check_bytecode.sh` on the compiled classes and APK (the CarPlay app in `carplay/` has its own, `carplay/guard/check_carplay.sh`, see "CarPlay app") (the logger has its own pair in `capture/tools/`; `app/tools/test_guards.sh` checks that the guards still refuse known bypasses). The Gradle build runs the same scripts at the same points and also refuses any library in the APK (`buildSrc/src/main/java/app/binnacle/gradle/Guards.java`); `app/build.sh` and `capture/build.sh` still run them too. Never weaken or bypass them.

A read-only replacement instrument cluster / dashboard app (plus tooling) for the **Carview 10.25" Tesla Model 3/Y Android cluster** (ZIQI "A007" ROM). It shows live car data taken from the stock CAN app and launches CarPlay / Android Auto / the camera, running as an alternative Home app. It never modifies the stock system.

## The unit
- Carview 10.25" (sold by smeshmega), ODM **ZIQI A007**. SoC **Unisoc UMS512**. Android **10** under the hood (SDK 29) despite a "12" label. SELinux **permissive**, `userdebug`, root via `su 0` (note: `su 0 <cmd>`, not `su -c`).
- Stock dash = `com.xbs.launcher1` (Home). Car data app = `com.xbs.canapp`, which reads the MCU over serial `/dev/ttyHS0` and decodes CAN frames.

## How we read car data — READ ONLY
- Bind the **exported** service `com.xbs.canapp` (action `com.xbs.canapp.action.mcuservice`). AIDL: `com.mcu.iinterface.aidl.IMcuService` (helper `com.mcu.iinterface.McuManager`). Call `regPropIdList(Messenger, int[] codes)`; data arrives on the Messenger as `Message`s where `msg.what` = code and `msg.getData()` = a `Bundle` of fields. Call `unregPropIdList(Messenger)` to stop.
- Permission `com.xbs.permission.READ_CAN_DATABASE` is `protectionLevel="normal"`, so **any app** (our own signing key) can receive the data. No platform signature needed.
- Field map: **docs/FIELD_MAP.md**.

## READ-ONLY RULE (hard requirement)
The app only ever **registers and receives**. It must **never** call the write/tx side:
- never `IMcuService.txMessengerPack / txGeneralProtocol / txPerformUartPack / txUpdateProtocol / setUartNormalTransmitEnable`
- never the native MCU serial write (`com.mct.serial.headunit.McuSerial.writeData` / its `C()` enqueue)
- never write via `content://com.xbs.can.provider`
- never use the CarSetUp (`com.xbs.carsetup`) settings that push values to the car. (The dash only READS `Settings.System xbs_carmsgdisppost`, the CarPlay layout, in `StockScreens`; `check_readonly.sh` allows that one read and nothing else. It does not open the car-setup screen, because that screen also holds settings the CAN app forwards to the MCU.)

No bytes ever go onto the vehicle CAN bus. MCU writes only as below.

## MCU writes (owner rule, 1 Nov 2026)
A write to the dash's own MCU is **acceptable but not preferred**: the owner accepts the small risk to make the dash easier to use. Each one is still a deliberate exception:
- prefer anything that avoids the MCU (an Android setting, an intent, a stock app's own screen);
- **confirm with the owner before assuming any MCU write**: bring the exact message, what it does, and the evidence it stays on the dash (best: it mirrors what a stock app already sends for the same action), and wait for a go on that specific message;
- never a message that is, or could be, forwarded onto the CAN bus or changes anything in the car;
- the guards stay as strict as they are: an approved message is added as one pinned exception (exact call and payload), never a general write path, and `test_guards.sh` gets a case proving any other write is still refused;
- listed with its undo in `docs/UNIT-CHANGES.md`.
Approved so far (none of them from the dash app itself):
- the CarPlay app's (`carplay/`, xcertplay) call state: ZLink's own `com.zjinnova.zlink` broadcast with `phoneMode=carplay_wireless` and `status=PHONE_CALL_ON` / `PHONE_CALL_OFF`, addressed to `com.xbs.canapp` only (the CAN app then sets the MCU's call mode, as it does for stock ZLink). OFF once at xcertplay start and after each ON it sent. Owner OK 4–5 Nov. The Siri message (142) is **not** approved. Listed in `docs/UNIT-CHANGES.md`.

## Dash-local writes (owner rule, 31 Oct 2026)
The absolute line is the car: nothing ever reaches the CAN bus, and the MCU / canapp write side only under "MCU writes" above; the guards stay as strict as they are. Changes that stay **on the dash itself** (an Android setting, a system property, another app's component or app-op, a file in the app's own storage) are allowed, but only when:
- the owner has approved that specific change;
- it is pinned in the guards (a fixed `LocalShell` command, or an exact allow-list entry), never built from caller text;
- it is opt-in for users, says what it does, and can be undone from the app;
- it is listed with its undo in `docs/UNIT-CHANGES.md`.
Approved so far: Bluetooth auto-connect (`settings put system xbs_isautoconnect`, via `LocalShell`), End CarPlay (Wi-Fi off/on, via `LocalShell`), Wi-Fi auto-connect scans off during CarPlay and on again (`service call wifi 58 i32 0/1`, Android 10 only, via `LocalShell`, on by default with a switch to turn it off (owner OK 4 Nov, default on 5 Nov); the Wi-Fi icon runs `service call wifi 58 i32 1` then End CarPlay's Wi-Fi off/on to rejoin home Wi-Fi, or `service call wifi 58 i32 1 && svc wifi enable` while CarPlay runs with the pause off) screenshots from the hidden power-bar button (`mkdir -p /sdcard/Binnacle/screenshots && screencap -p …/$(date).png`, via `LocalShell`, Advanced → Screenshot on power bar tap, off by default, owner OK 5 Nov), xcertplay's location app-op back to allow (`appops set --uid com.shilapi.xcertplay COARSE_LOCATION allow`, via `LocalShell`, each time the dash links up with xcertplay: the unit resets it on every reboot and xcertplay update and wireless CarPlay's Wi-Fi Direct then fails; only with the signed xcertplay installed, owner OK 5 Nov) the camera decoder input and format (`CameraPane.setUpDecoder`: `2` to `/sys/ziqi/camera/channel` and `AHD_1080P_30` to `N_P_pre_format`, world-writable sysfs on the dash, owner OK 5 Nov) and the start-up media volume (`StartupVolume`: `AudioManager.setStreamVolume(STREAM_MUSIC, level)`, after unmuting music if the CAN app muted it, at start, when the car's Bluetooth audio connects and when the screen comes back on after the car sleeps, then for a minute after each again if music is zeroed or muted (owner, 8 Nov: it was 0 on getting in), 100% by default, Settings → Start-up volume, owner OK 4 Nov: Android's own music volume, which the CAN app also sets locally for the wheel keys; not the car-setup "speaker level", which goes to the MCU). Anything the CAN app forwards to the MCU (backlight mode, speaker level, ambient light, camera type/trigger, night mode) is an MCU write: only under "MCU writes" above, never assumed.

## Must-keep features — never break these
- **Forward/reverse camera**: separate app `com.xbs.frontcam`, activity `com.xbs.frontcam.CameraActivity` (also responds to intent `com.xbs.action.reqcam`). Auto-shows on Drive via the CAN `frontcamstate` flag — a replacement Home re-does that (watch the flag, launch the camera). Independent of the Home app otherwise.
- **CarPlay / Android Auto**: CarPlay opens xcertplay (`com.shilapi.xcertplay/.CarPlayHostActivity`) when it is installed (owner, 1 Nov), otherwise ZLink (`com.zjinnova.zlink`, the licensed *xinbasi-a007* build, which also does Android Auto). Launch by intent, or, when xcertplay is signed with the dash's key, draw it in the dash (see "CarPlay in the dash"). Never uninstall or disable ZLink; with xcertplay installed it is only hidden from Binnacle's app list.
- Keep the stock launcher `com.xbs.launcher1` installed as the **fallback Home**.

## CarPlay in the dash (CarPlayLink, owner OK 4 Nov 2026)
The dash can draw CarPlay in its own window (centre or full screen) so it stays the top activity and the CAN app keeps the door pop-up hidden. xcertplay (an app on the unit) runs the session; `CarPlayLink` binds its `CarPlayEmbedService` and hands it a Surface, touch and wheel keys. This is the second binder exception after `CanFeed`, pinned the same way:
- one class (`CarPlayLink`), one `bindService` to the fixed component `com.shilapi.xcertplay/.CarPlayEmbedService`, one `transact` that refuses any code outside ICarPlayEmbed's 1..10 before touching the binder;
- state comes back on a Messenger the dash only receives on (never `Messenger.send`);
- both guards pin the class (source text; compiled opcodes and strings), and `test_guards.sh` has cases for a widened code check, another package, a changed txn, a Messenger send and a second transact.
The same Messenger brings what the iPhone is playing (title, artist, a small cover) for the right card's Now playing page, which only shows it (no buttons). `CarPlayAuto` (Settings → CarPlay auto-connect, off by default, issue #90) uses the same `start()` behind the dash at dash start and screen-on (after the car's Bluetooth audio is back, at most 20 s), shows CarPlay only once it streams (if set to "Connect & show"), and calls `disconnect()` if it hasn't connected within 90 s or xcertplay gave up, so a car without the paired iPhone sees nothing; xcertplay starts such a surface-less session at the first declared size. It needs xcertplay signed with the dash's key (the service is signature-protected); otherwise binding fails and the CarPlay button opens xcertplay's own screen as before. Nothing in this path reaches the car or the MCU.

## CarPlay app (carplay/)
`carplay/` is Binnacle's CarPlay app, package `com.shilapi.xcertplay`: a fork of [xcertplay](https://github.com/shilapi/xcertplay) (shilapi and contributors, GPL-3.0) merged in with its full history (owner decision, 5 Nov 2026: one repo, two apps, one release). It stays a **separate APK** with its own Gradle build (Kotlin, Compose, NDK), so the dash's guards keep checking only the dash's Java and the CAN feed and CarPlay code never share a process.
- **Guard:** `carplay/guard/check_carplay.sh` runs before every CarPlay build (`preBuild` in `carplay/mobile/build.gradle.kts`) and on the signed release APK (`release.sh`). It refuses any MCU/CAN API (IMcuService and its tx side, McuSerial, the CAN provider, car settings, serial ports), shell commands, system properties, settings writes, the local ADB daemon, car-property writes and the Siri call-state message. The head unit's apps are named only in `HeadUnitCallState`, which sends the one approved broadcast (pinned line by line, string literals pinned). Binder use only in the reviewed places (two `bindService` calls to its own services, `Messenger.send` only in `CarPlayEmbedService`, ContentResolver reads only, no service starts or raw transacts), every source set but tests scanned, no import aliases or member imports of settings/process/class-loader APIs. Reflection (by method, field, constructor or method handle) only in the files that use it today; one native library from hash-pinned sources, whose `open()` takes only `/dev/i2c-N` (checked in Kotlin and C). `carplay/guard/test_carplay_guard.sh` plants each bypass and expects a failure; `release.sh` runs it. Any change to these pins needs review, and a new MCU message needs the owner's go first (see "MCU writes").
- **Signing:** `release.sh` builds it unsigned (`-Pxcertplay.unsigned=true`) and signs it with the dash's release key (the dash's `CarPlayLink` needs the same key). Bump `versionCode` in `carplay/mobile/build.gradle.kts` whenever it changes: `release.sh` and `deploy.sh` stop if `carplay/` changed since the last `v*` tag (Markdown aside) without a higher versionCode.
- **Release:** the same GitHub release as the dash carries `BinnacleCarPlay.apk`; `binnacle-update.txt` lists its `carplayVersionCode`, `carplayVersionName`, `carplaySize` and `carplaySha256`.
- **Upstream:** post nothing upstream (no issues, PRs or comments on shilapi/xcertplay). To take an upstream fix: `git fetch https://github.com/shilapi/xcertplay master` and merge it with `git merge -X subtree=carplay/ FETCH_HEAD` (or cherry-pick), then run the guard. Keep `carplay/README.md`'s credit and fork-change list up to date with each CarPlay PR.
- **PRs that touch `carplay/` must be merged with a merge commit** (not squash), or its imported history is lost.
- Compile its modules one at a time when checking without Gradle (`shared`, then `common`/`mobile` against it): a combined compile hides a cross-module `internal`.

## In-app updates (Updater)
Advanced → Updates checks the **latest** GitHub release of this repo, on a tap only (no background checks), and installs it through Android's `PackageInstaller`: the APK is streamed into the install session (no file written by the app), must match the size and SHA-256 in the release's `binnacle-update.txt`, and the session is locked to this app's own package name, so Android accepts only Binnacle itself, signed with the same key, at a higher versionCode, and shows its own confirm screen. One pinned exception: the same session may instead be locked to the CarPlay app (`com.shilapi.xcertplay`, `BinnacleCarPlay.apk` from the same release, `carplay*` lines in the info file), only when it is already installed, so Android again insists on the installed copy's key; `target()` is the one place that picks between the two names, pinned in both guards with `test_guards.sh` cases. Only in Park (installing restarts the dash). It needs `REQUEST_INSTALL_PACKAGES` and the user's "Install unknown apps" switch for Binnacle (a dash-local setting the user turns on in Android's own screen; listed in docs/UNIT-CHANGES.md). Not root and not `LocalShell`: no new shell command. The guards pin it like CarPacks: network and the installer only in `Updater`, only `RELEASE_BASE + INFO/APK/CARPLAY_APK`, GET only, `setAppPackageName(target(c, carplay))` exactly once; `test_guards.sh` has cases for each. Releases: `release.sh` writes `build/release/github/{Binnacle.apk,BinnacleCarPlay.apk,binnacle-update.txt}`; publish all three as the latest release (bump versionCode first); `./deploy.sh release` pulls main, checks the versions, builds and publishes it. Car-image releases must be published with `--latest=false` (`./deploy.sh cars`), or the dash would look for an update there. Details: docs/UPDATES.md.

## ADB / network facts
- `adb connect <unit-ip>:5555` (persistent, no key auth on the LAN).
- **Single Wi-Fi radio**: wireless CarPlay brings up a SoftAP that drops the dash off home Wi-Fi, so ADB over the LAN dies while wireless CarPlay is connected.
- **Android Bluetooth stack is OFF by default**: Bluetooth calls and audio go through a separate Goodocom serial module. Setting `persist.car.use_system_bt=2` (dash-local, then reboot) turns Android Bluetooth on alongside it, with Bluetooth LE; on trial on the owner's unit since 31 Oct.
- Not in the data feed: **true range (km)** and **brake/stop-light state**. On this car `batterylevel` is stuck at 77, so the dash decodes the battery % from code 11 `jhmail` instead, until `batterylevel` is seen to change (it works on other cars, issue #91; `BatteryDecoder.pick`/`LevelWatch`) (`BatteryDecoder`, a table recorded during a 13% → 100% Supercharge on 30 Oct; see docs/FIELD_MAP.md).

## Local shell (LocalShell)
- The unit's own ADB daemon listens on all interfaces at 5555 with no auth, so the app reaches it on 127.0.0.1 and runs a **fixed** list of shell-user commands (root only for the pinned unit-setup ones below), e.g. End CarPlay = `svc wifi disable && sleep 2 && svc wifi enable && echo BINNACLE_OK` (run() requires the marker) (never force-stop ZLink: it breaks the Goodocom Bluetooth until a reboot).
- `check_readonly.sh` pins the exact command list, keeps sockets in `LocalShell` only, and forbids caller-supplied text. Never add a command that touches the car, the MCU or CAN. A dash-local setting or property is added only under the "Dash-local writes" rule above (owner approval, pinned, opt-in, reversible, documented).
- **Root (owner OK 8 Nov):** the unit-setup commands are the only `su 0` ones, each pinned in both guards with its undo (`UnitSetup`, `AdbFirewall`; `test_guards.sh` refuses another root command or a widened one): keep ADB on after restart (`persist.adb.tcp.port`), ADB off the Wi-Fi (`iptables`/`ip6tables` DROP on 5555 except `lo`, at every dash start; Settings → Unit → Network ADB removes it, off by default), GPS crash dumps off and `/data/corefile` cleared, stock `CameraActivity` disabled, `persist.car.use_system_bt=2`, `persist.bluetooth.disableabsvol`, and CarPlay calls (CALL_PHONE, xcertplay's calling account on and default, stock in-call screen off; shell user except the in-call screen). Opt-in from setup's "Set up the unit" step or Advanced → Unit setup; listed in docs/UNIT-CHANGES.md.

## Steering-wheel input
`canapp` injects **standard Android KeyEvents** from the MCU. Scroll up/down = `DPAD_UP`(19)/`DPAD_DOWN`(20); right tilt (OK) = `ENTER`(66); left tilt = `BACK`(4); plus volume/media/home. Handle with normal `onKeyDown` / focus navigation — no special integration.
